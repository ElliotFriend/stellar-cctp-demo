    • §1 Cold open

    Three ways to move a dollar

    Lock & wrap

    Lock on A, mint a wrapped token on B. Wormhole's portal bridge.

    Liquidity pool

    Deposit to an LP on A, withdraw from the matching LP on B. Allbridge Core.

    Burn & mint

    Burn the real USDC on A. Circle authorizes a mint of native, canonical USDC on B.

    Why us As of May 2026, Stellar is a CCTP V2 destination and source (domain 27).
  • Both of the first two leave a big pile of USDC sitting idle. That pile grows into a honeypot, and honeypots attract exploits.
  • No wrapped-USDC dead-end token. No pool that can run dry or get compromised.
  • Say finally a CCTP V2 destination and source: it was a long wait.
  • "So how does chain B know it's allowed to mint? That's the whole trick, and it's three moving parts."

    • §2 Mental model

    Three actors, three steps

    1 · Burn Source chain deposit_for_burn
    → TokenMessengerMinter
    2 · Attest  ·  Circle (Iris) messageattestation
    3 · Mint Destination receive_message
    → native USDC
    • The burn emits a structured message into the MessageTransmitter, a generic cross-chain bus: N units burned on domain X, for recipient R on domain Y.
    • Circle waits for source finality, then signs an attestation. Arc: seconds. Ethereum and its L2s: up to ~20 min. Finality, not Circle being slow.
    • Anyone can carry (message, attestation) to the destination and trigger the mint.
  • Iris = the name of Circle's off-chain attestation API.
  • Favourite outlier: StarkNet takes 4 to 8 hours to reach finality. You're always waiting on the source chain, not on Circle.
  • One breath on naming: the same contract is TokenMessengerMinter on Stellar, TokenMessengerV2 on EVM, and TokenMessengerMinterV2 on Solana. Use each chain's own spelling when you're looking at that chain's code.
  • On EVM the minting is a separate TokenMinterV2; on Stellar the one contract does both burn and mint.
  • Emphasize permissionless: the mint isn't Circle's job unless you ask it to be (§4).

    • §2 Mental model

    Every destination takes the same pair

    EVM      MessageTransmitterV2.receiveMessage(bytes message, bytes attestation)
Solana   MessageTransmitterV2.receiveMessage(...)  // CPIs into TMM
Stellar  MessageTransmitter.receive_message(caller, message, attestation)

// ...but INTO Stellar we never call receive_message directly:
Stellar  CctpForwarder.mint_and_forward(message, attestation)

    Verify Circle's signature, mint. The only twist is inbound, where the same call also does the last hop to a G‑account, which is the next section.

    • §2 Vocabulary

    Fast vs Standard is one integer

    min_finality_threshold = 2000

    Standard. Wait for hard finality on the source chain. No extra fee.

    min_finality_threshold = 1000

    Fast. Circle attests earlier for a small fee, backed by its own guarantee. You'll see the number go over the wire in the demos.

    Caveat Fast only means something when the source is a slow-finality chain. Hold that thought until Solana.
  • Payoff lands in §7c: on an outbound transfer, the toggle is effectively cosmetic.

    • §3a Stellar realities

    A CCTP mint can't safely target a G‑account

    • On EVM, a mint recipient is a 20-byte address. EOA or contract, the mint doesn't care. On Stellar, CCTP mints to a contract address (C…) and mintRecipient is a raw 32-byte key.
    • A CCTP message cannot distinguish a G address from a C address, and the mint path expects a contract it can call into.
    • The fix: inbound mints to a CctpForwarder (CA66…4VSZ). The real G address travels in hook data. The Forwarder mints to itself, then pays out, atomically and permissionlessly, in one call.
    Lose funds Put a bare G address in mintRecipient and the funds land somewhere that can't receive them. You brick the transfer. Single most dangerous mistake in the integration.
  • Analogy for this room: same reason you can't payment an asset to a G account with no trustline. The destination has to be prepared to receive.
  • The Forwarder is the thing that's already prepared, and it does the last hop for you. Caller just pays the Stellar tx fee.

    • §3b The most important bytes in the repo

    Where the recipient actually rides

    mint_recipient  · 32 bytes

    CctpForwarder contract  CA66…4VSZ

    hook_data

    reserved 24 bytes, zeros
    version u32 · 0
    length u32
    "GB…" strkey UTF‑8 text, 56 bytes
    Lose funds The strkey as UTF‑8 text (the literal GB… string), not the decoded 32-byte key. Send decoded bytes and funds are stuck.
  • "That surprised me. It's Circle's chosen convention for Stellar."
  • Field widths on the diagram are not to scale: the strkey is 56 of the bytes.
  • I validate the strkey before building the burn, because there's no undo.

    • §3b src/lib/stellar/recipient.ts

    Twelve lines between you and stuck funds

    export function encodeStellarForwarderHookData(stellarStrkey: string): Hex {
    if (!StrKey.isValidEd25519PublicKey(stellarStrkey)) {
        throw new Error(`Invalid Stellar account: ${stellarStrkey}`);
    }
    const magic       = pad('0x', { size: 24 });
    const version     = pad(toHex(0), { size: 4 });
    const recipientHex = stringToHex(stellarStrkey);  // the "GB..." strkey, as UTF-8
    const lengthField = pad(toHex((recipientHex.length - 2) / 2), { size: 4 });
    return concatHex([magic, version, lengthField, recipientHex]);
}
  • Circle's own writeup: developers.circle.com/cctp/references/stellar. Their docs carry the same warning: set mintRecipient to a user account and funds are permanently stuck.
  • Muxed M addresses are G-flavored, so the same rule applies.

    • §3b The rule

    Into Stellar: always depositForBurnWithHook

    The G address exists only in the hook, and both hookless options lose money.

    G address in mintRecipient

    Bricks. Nothing there can receive it. (§3a)

    Forwarder, no hook

    No recipient to pay out to. Errors HookDataEmpty.

  • This is the one slide to repeat if the room takes nothing else away.
  • Holds for both sources we're about to demo: EVM and Solana.

    • §3c Stellar realities

    One field, three opinions

    Destination What goes in mintRecipient Encoding
    EVM the 20-byte EOA / contract address right-aligned in 32 bytes
    leftPad32FromHex
    Solana the recipient's USDC ATA, not the wallet raw 32 bytes, left-aligned
    a pubkey already fills 32
    Stellar always the Forwarder's C… id; real recipient in hook data decoded to raw 32 bytes
    strkeyToBytes32, not 3b's UTF-8
    New vocab On Solana you don't hold USDC at your wallet address. You hold it in an Associated Token Account derived from wallet + mint. The burn's recipient must be that ATA.
  • "Every chain has a 32-byte slot and its own opinion about how to fill it."
  • Two fields, two opposite conventions. A message slot (mintRecipient, destinationCaller) takes the decoded bytes of the Forwarder's C… id. Hook data sends the recipient strkey as UTF-8 text. Easy to conflate, and either mistake loses funds.

    • §4 developers.circle.com/cctp/concepts/forwarding-service

    Make the destination transaction disappear

    • Normally someone pays to submit the mint. For a recipient with no gas token on the destination, that's an onboarding wall.
    • Circle's Crosschain Forwarding Service is a relayer: set a small forward fee, tag the burn with a cctp-forward marker in hook data, and Circle submits the mint itself. USDC just appears.
    • Who receives it doesn't change. Still the ordinary mint_recipient from the burn args. The flag carries no address.
    Two gotchas The relayer consumes ~the full maxFee, so size it to the ?forward=true quote. And destinationCaller must be zero; setting it disables forwarding.
  • In code: encodeCctpForwardHookData(): a 24-byte reserved region carrying ASCII cctp-forward, version 0, length 0.
  • App side has no destination step at all. Poll the recipient's balance until the relayer's mint lands.
  • The flag only says "please forward this," and padding on maxFee is paid, not refunded.

    • §5b contracts/stellar/cctp-wrapper/src/lib.rs

    Forty lines of Rust, one signature

    pub fn approve_and_deposit(
    env: Env, caller: Address, usdc: Address, tmm: Address, amount: i128,
    destination_domain: u32, mint_recipient: BytesN<32>,
    destination_caller: BytesN<32>, max_fee: i128, min_finality_threshold: u32,
) {
    caller.require_auth();

    // approve an allowance so the TokenMessengerMinter can transfer_from our caller
    let live_until_ledger = (env.ledger().sequence() + 50).next_multiple_of(50);
    token::Client::new(&env, &usdc).approve(&caller, &tmm, &amount, &live_until_ledger);

    TmmClient::new(&env, &tmm).deposit_for_burn(
        &caller, &amount, &destination_domain, &mint_recipient,
        &usdc, &destination_caller, &max_fee, &min_finality_threshold,
    );
}
  • require_auth: both inner calls act on behalf of caller, so Soroban's auth framework needs one signature covering the tree, and Freighter collects it in one prompt. On EVM there is no equivalent.
  • live_until_ledger rounded to the next multiple of 50 to avoid simulate-vs-submit ledger mismatches. The allowance is fully consumed by the burn anyway.
  • TmmClient is a typed Rust-to-Rust interface, generated with stellar contract bindings rust.
  • usdc is an arg because the TMM itself takes it that way; tmm is an arg because I don't know how permanent Circle's addresses are. Flip side: the frontend must supply trusted addresses, so for mainnet you'd pin or govern these.
  • There's a twin, approve_and_deposit_with_hook, identical plus a trailing hook_data: Bytes, and that's what Demo D uses.

    • §5b If time

    Same UX goal, very different price

    Soroban

    One signature authorizes a sub-tree. approve + deposit_for_burn become inner calls of one invocation. No extra primitive needed.

    EVM: bridgeWithPermit()

    Four calls bundled: usdc.permit → transferFrom → approve → depositForBurnWithHook. The user signs an EIP‑2612 typed message off-chain; the contract redeems it.

    Caveat permit only works because USDC implements EIP‑2612. Not every ERC‑20 does.
  • Safe cut #1. You'll have shown the wrapper concept already in §5b/§5c.
  • On a plain EOA, approve and the burn are two transactions, full stop, unless you add a contract or wallet batching.

    • §5c "1 tx (wrapper)"  ·  demo

    Same burn. Same args. One prompt.

    On-chain

    Nothing changed. The approve and the deposit_for_burn both still happen, now as inner calls inside one invocation of approve_and_deposit.

    In the wallet

    Two Freighter prompts become one. One signature, one network fee. Destination side is byte-for-byte the same as §5a.

    Be precise This isn't cheaper gas and it isn't cryptographically clever. It's bundling. But one prompt vs two is the difference between "this feels like an app" and "this feels like a blockchain."

    Two things must be true, or funds are gone

    burnArgs = [
  amount,             // uint256, 6 dp
  27,                 // destinationDomain = Stellar
  forwarderBytes32,   // mintRecipient     = CctpForwarder  ← must be the forwarder
  cfg.usdc,           // burnToken (per-chain USDC)

  finalityThreshold,
  hookData,           // encodeStellarForwarderHookData(yourGAddress)
]
    Why both destinationCaller = the Forwarder means only the Forwarder can submit the mint, which guarantees mint_and_forward's payout logic runs instead of someone minting to the Forwarder and stranding the funds.

    • §6b The EVM UX ladder

    Three ways to bundle approve + burn

    Flow User sees On-chain txs Needs
    2 tx (direct) 2 confirmations 2 nothing extra
    1 tx (permit) 1 signature + 1 confirmation 1 our CctpWrapper on this chain
    1 click (sendCalls) 1 confirmation 1 wallet supports EIP‑5792
    Destination Always identical: poll Iris → mint_and_forward(message, attestation) → USDC at your G address. No receiveMessage to call by hand.
  • permit: one signature costs no gas, it's just a typed message. Half the gas of the 2-tx path.
  • sendCalls = EIP-5792 wallet_sendCalls: hand the wallet both calls. Smart wallet or EIP-7702 → one atomic tx; plain EOA → one prompt, two txs behind it.

    • §7a Solana → Stellar

    No approve, fifteen accounts

    • No approve step. depositForBurn burns directly under the owner's signature via CPI. One transaction, plus a throwaway co-signer keypair for the event account.
    • ~15 accounts and several PDAs (program-derived addresses) go in. I don't hand-roll them: a typed client generated from Circle's Anchor IDL with Codama.
    • Same into-Stellar invariant as EVM: mintRecipient == destinationCaller == the Forwarder, real G address in hookData.
    Payoff The Stellar side is the identical mint_and_forward from Demo B. Zero new Stellar code.
  • Codama is Solana's analog of stellar contract bindings typescript: interface description in, typed instruction builder out.
  • Zero new Stellar code on the mint side is what routing everything through the Forwarder buys.
  • Good place to remind the room that the Forwarder is the single inbound chokepoint by design.

    • §7b Stellar → Solana

    On Solana, the receive is not a mint

    • handle_receive_finalized_message transfers USDC out of a shared custody_token_account that Circle pre-funds, and pays its fee out of it too. There is no mint_to in the instruction's account list at all.
    • So "burn-and-mint" is really burn-and-release-from-custody. Circle keeps a float of already-minted USDC waiting to be handed out.
    • It's an implementation detail of how CCTP maps onto Solana's token model. Nothing materially different for a developer, but a fun discovery.
    Failure you can't cause If Circle's custody float is underfunded on devnet, the transfer reverts. That's their liquidity, not our bug.
  • Genuinely interesting protocol detail for this room.
  • Custody funding is the one variable Circle controls, so if the receive fails live, say that plainly and cut to the recording.

    • §7c Coming clean

    From Stellar, the Fast toggle is cosmetic

    • Every flow has a Fast/Standard toggle, mapping to the minFinalityThreshold you saw in the args: 1000 vs 2000.
    • But when the source is Stellar, Circle attests at the Standard threshold regardless of what we request, because Stellar already has fast finality. Circle lists Fast Transfer as N/A for Stellar.
    • Fast only does something observable when the source is a slower chain, Base for instance.
    Why keep it I left the toggle in so the parameter is visible, but I'd be lying if I said it changed outbound timing.
  • The caveats are the credibility. Don't smooth this one over.

    • §9 Recap

    In one breath

    • CCTP is burn → attest → mint. Canonical USDC both sides. No wrapped token, no pool.
    • Inbound to Stellar routes through the Forwarder, because a raw G address bricks funds. The recipient rides in hook data, so it's always depositForBurnWithHook. Domain 27.
    • A wrapper contract collapses approve + burn into one signature. Trivially on Soroban via the auth tree; on EVM only via permit.
    • Forwarding removes the destination step, for Stellar as a source, to EVM or Solana, today.
    • Solana is real, but it receives from custody, not a fresh mint.
  • One breath. Don't re-teach. This is a landing, not a lesson.
